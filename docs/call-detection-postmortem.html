Call Detection Postmortem

Why the post-call popup wasn't appearing, what six root causes turned out to be, and the one that's still open on this specific device.

Branch
feat/inventory-manager
Device
Tecno Spark 20C (Transsion / HiOS)
Package
com.aistudio.callpopup.crm
6 fixed & verified
1 open — OEM restriction

Reported symptom

"The app must show the popup with current permissions — it still fails to capture missed calls and others. The service should never sleep."

Two separate complaints turned out to share no single cause: the service sometimes wasn't running at all, and when it was, the popup itself could fail to render. Six distinct, independently-confirmed bugs were found across both. This document walks through each one in the order it was found, since each fix exposed the next problem underneath it.

Findings

1
Notification permission silently disabled detection
Resolved
CallMonitorService never started for anyone who denied the notification prompt

PermissionUtils.getRequiredRuntimePermissions() bundled POST_NOTIFICATIONS into the same set as READ_PHONE_STATE / READ_CALL_LOG / READ_CONTACTS, and every call site gated CallMonitorService.start() on that combined set. Denying just the notification prompt — common, and not actually required for detection to work — silently prevented the service from ever starting, with no error surfaced anywhere.

Fix

Split into a critical set (phone/call-log/contacts, gates service start) and a full set (adds notifications, drives the permission-request UI only).

b7b3785
2
Call-log query raced the OS's own write
Resolved
Missed calls specifically — the write can land a beat after the state goes IDLE

The number/duration for a just-ended call was resolved by querying CallLog.Calls.CONTENT_URI exactly once, immediately on the IDLE transition. For missed calls in particular, Android sometimes writes that log entry a second or two later, so the single query could return nothing or a stale prior call.

Fix

CallLogHelper.getMostRecentCallWithRetry() retries for ~2s, accepting the first row timestamped at or after the call actually started.

b7b3785
3
Screened calls never reached the telephony listener
Resolved
A call rejected below the telephony API never surfaces a RINGING state at all

Detection relied solely on TelephonyCallback watching for RINGING → IDLE. A call rejected by the carrier, Do Not Disturb, or OEM call-screening never generates a RINGING event on-device — the only trace is a MISSED row appearing later in the call log, which the telephony-only approach had no way to see.

Fix

Added a second, independent path: a ContentObserver on CallLog.Calls.CONTENT_URI that triggers directly off a new MISSED row. Both paths converge on one showPopupForCall(), deduped by phone number within an 8s window.

7027fe6
4
The overlay window could hang the entire app
Resolved
Confirmed on-device: a Binder call into this OEM's WindowManagerService never returns

Diagnosed live over adb by inserting a fake MISSED row and watching the process. The pipeline ran correctly and started FloatingWindowOverlayService — which then froze. top showed the process sitting in kernel state D (uninterruptible sleep) at 0% CPU, unchanging across repeated samples: a genuine hang, not slowness.

 PID   USER      S  %CPU  TIME+   PROCESS
25159 u0_a278   D  0.0   0:35.79 com.aistudio.callpopup.crm

Because that Service originally shared a process — and a main thread — with CallMonitorService, the hang froze call detection along with the overlay. This exactly matched the original report that the popup "only shows right after opening the app": each reopen bought one working attempt before the process wedged again.

First attempt — broke the overlay outright

Moved the WindowManager/ComposeView work to a background HandlerThread. Compose's WindowRecomposer calls LifecycleRegistry.addObserver() internally during onAttachedToWindow(), and AndroidX Lifecycle throws unconditionally if that happens off the main thread — ComposeView.addView() genuinely cannot leave main.

FATAL EXCEPTION: FloatingOverlayWindowThread
java.lang.IllegalStateException: Method addObserver must be called on the main thread
  at androidx.lifecycle.LifecycleRegistry.enforceMainThreadIfNeeded
  at androidx.compose.ui.platform.WindowRecomposer_androidKt.createLifecycleAwareWindowRecomposer
Actual fix — process isolation

FloatingWindowOverlayService now runs in its own process (android:process=":overlay"). A hang there can no longer take CallMonitorService's process down with it. AppDatabase gained enableMultiInstanceInvalidation() so Room's queries stay in sync across the process boundary.

b26a2d2
5
One failed coroutine silently broke all future detection
Resolved
Worked exactly once per service start, then went completely silent — no crash, no log

CallMonitorService's long-lived CoroutineScope used a plain Job(). Any uncaught exception in one launched coroutine cancels a plain Job's whole subtree — every subsequent scope.launch { } becomes a silent no-op, forever, with nothing written to logcat. That's a precise match for what testing showed: the CallLog-observer path fired once after each fresh start, then nothing — for artificial triggers and a genuine cellular missed call.

Fix

Switched to SupervisorJob() plus a CoroutineExceptionHandler that logs any future failure instead of letting it vanish.

e1909c7
6
The new :overlay process crashed on its own Application init
Resolved
Fallout from the process split in #4 — caught the same night, before it shipped

Android runs Application.onCreate() fresh in every process, including the new :overlay one. It unconditionally called WorkManager.getInstance() to schedule the watchdog worker — but WorkManager's auto-init ContentProvider only runs in the main process. The :overlay process crashed 3 seconds after spawning, every time, before the popup could ever render.

FATAL EXCEPTION: main
Process: com.aistudio.callpopup.crm:overlay, PID: 15505
java.lang.RuntimeException: Unable to create application com.example.CallPopupApplication:
  java.lang.IllegalStateException: WorkManager is not initialized properly.
Fix

Added an isMainProcess() check; the watchdog now only schedules from the main process.

f296a89

Confirmed working

With all six fixes in place and the app in the foreground, an injected MISSED call log row ran the full pipeline end to end: ContentObserver → checkForNewMissedCall → showPopupForCall → FloatingWindowOverlayService spawning cleanly in its own process → addView succeeding. The popup rendered, and you confirmed it visually on-screen.

I CallMonitorService: checkForNewMissedCall: recent=RecentCallInfo(number=+15550192856, callType=MISSED)
I CallMonitorService: showPopupForCall: overlayEnabled=true overlayPermissionGranted=true
I FloatingWindowOverlay: onStartCommand: canDrawOverlays=true
I FloatingWindowOverlay: showOverlay: addView succeeded

Still open

Background delivery is silent on this device
Open
Every standard Android mechanism checked is already correctly configured — and delivery still fails

With the app merely backgrounded (service alive, not swiped away), neither an injected call-log row nor a genuine cellular missed call produced any response: zero CPU, zero log output, not even routine GC noise. Thread inspection ruled out a hang — every thread, including the dedicated detection thread, was healthy and idle.

A minimal standalone reproduction app was built specifically to isolate this from mobile-crm's other complexity (Room, WorkManager, WebSocket, telephony) - just a bare, permission-less BroadcastReceiver and an overlay Service, nothing else. It rigorously ruled out every documented cause, one at a time:

$ adb shell dumpsys deviceidle whitelist | grep aistudio
user,com.aistudio.callpopup.crm,10287                    # Doze exemption: granted

$ adb shell dumpsys deviceidle | grep mState
mState=ACTIVE mLightState=ACTIVE                          # System not even in Doze right now

# Phone Master -> App Launch (Autostart): "Allowed"          # not the blocker
# Settings -> App info -> Battery: "Unrestricted"             # not the blocker

$ adb shell am broadcast -n com.aistudio.popuptest/.TriggerReceiver \
    -a com.aistudio.popuptest.ACTION_SHOW_POPUP --es variant same
Broadcasting: Intent { ... cmp=com.aistudio.popuptest/.TriggerReceiver ... }
Broadcast completed: result=0
[TriggerReceiver never logs onReceive() - with or without an active foreground service]

That last test is the one that matters: a fully-explicit broadcast, naming the exact component, to a receiver with no permission requirement at all, sent while a foreground service was confirmed running - and it still never fires. Explicit broadcasts and foreground-service presence are supposed to be exempt from Android's standard background-execution limits. Ruling all of this out leaves only one explanation: Transsion/HiOS enforces a background-process restriction beneath every documented Android API, one an app cannot detect, request an exemption for, or work around from code.

Next steps

  1. 1
    Not a settings hunt anymoreAutostart, Battery Usage, and the Doze whitelist are all confirmed already correct on this device via adb - there is no remaining toggle to go find.
  2. 2
    Test on a second, less locked-down deviceThe one remaining way to confirm this is fully device-specific rather than something still to chase in the app - the code itself is proven correct (foreground popup renders end to end).
  3. 3
    If it must work reliably on this exact deviceThe only architecture known to get materially stronger background guarantees on Android is a full InCallService/default-dialer implementation (see the separate note on why com.aistudio.smartcaller.xkzpmv uses that approach) - a much larger scope and risk increase, not a small fix.
